# Follow-up bridge security audit

Review dates: 7–8 September 2026 (UTC). Baseline: `802a5ea488fd629c0253c3c97303798b6033ed16`.
Implementation and review history: [pull request #2](https://github.com/tiagobeltraoacioli-sketch/bloch-l2-bridge/pull/2).

## Assessment

Six additional findings were addressed in the deposit watcher and genesis
configuration boundary. The review also reduced duplicate Merkle hashing and
added executable EVM security tests and mandatory CI gates. This is an internal
source-code review with executable regressions, not an independent external
audit, formal verification, or approval to handle real funds.

The baseline already contained useful safeguards: exact atom conversion,
strict deposit decoding, recomputed withdrawal leaves, bounded-depth Merkle
verification, a shared Solidity reentrancy lock, and an explicitly blocked
release checklist. The follow-up findings concern state accepted around those
mechanisms. No demonstrated loss of live funds or new critical/high-severity
contract exploit is claimed. The code is a custodial design scaffold; severity
below describes plausible impact when its interfaces are integrated into a host.

## Scope and trust boundaries

Reviewed production paths: all eleven Rust modules, the three Solidity
contracts, deployment configuration, compiler harness and dependency lockfile.
Reviewed the previous audit and test coverage; preserved its historical report
as `AUDIT.md`. The scope is this repository at the identified commit. External
Bloch consensus, sequencer, proving, signer and RPC implementations were not
available in this checkout and were not audited as part of this review.

| Boundary | What is checked here | What remains the host's responsibility |
|---|---|---|
| L1 blocks → watcher | Heights, parent linkage, stable sampled endpoints, exact envelope and vault output rules | Authenticate blocks/transactions against an own node, choose the intended L1/genesis, bound RPC latency and block sizes |
| Persisted snapshot → watcher | Deposit identity, journal membership, chain, amount/recipient, canonical K, phase, durable credit consistency; optional independent configuration binding | Atomic and authenticated storage, rollback protection, protected credit history and alarm logs |
| Watcher → L2 mint | Automatic tier and current local confirmations; no duplicate credit announcement per durable ID | Idempotent mint keyed by `(txid, first vault vout)`, safe recovery/outbox, global incident policy |
| Withdrawal → root/proof | Exact ABI preimage, Keccak, append order, historical roots and fixed-depth inclusion | Authenticate the epoch/chain/domain, prove the actual transition and account for native supply |
| Release observations → checklist | Anchor/root/epoch binding, amount-derived depth, inclusion, nullifier, freeze and supplied reserve statement | FRI verifier, authenticated observations, coherent accounting, rate limiter, payout transaction and custody policy |
| Config → compiler/genesis | Both mandatory predeploys and addresses, uniqueness, source confinement and source/bytecode pins | Trusted compiler, immutable source tree during checks, real genesis implementation and artifact provenance |

All transaction/chain inputs used in tests were synthetic local fixtures. No
keys were accessed, no live chain was probed for exploitation, and no deployment
or payout was performed. Tests executed through GitHub Actions because the local
editing environment had no Rust or Solidity compiler.

## Findings and remediation

| ID | Severity | Finding | Result |
|---|---|---|---|
| BRG-01 | Medium | Restored deposit state could bypass K or disagree with mint identity/history | Fixed; snapshot invariants and independently supplied config checked |
| BRG-02 | Medium | A surviving deposit remained creditable after losing confirmations | Fixed; demotion, explicit notification and preserved dedup/alarm history |
| BRG-03 | Medium | Missing/mixed source responses could mutate durable reorg state | Fixed; validate a staged suffix before committing; typed refusal |
| BRG-04 | Medium | An arbitrary reported tip could impose impractical work in one sync | Fixed; explicit per-call append/rewind limit and incremental catch-up |
| BRG-05 | Low | Genesis validation accepted missing, moved or duplicate bridge allocations | Fixed; mandatory bridge address and unique names/addresses enforced |
| BRG-06 | Low | Lexically confined paths could escape through symlinks | Fixed for existing sources; canonical filesystem containment checked |

### BRG-01 — Snapshot invariants did not cover the credit decision

`DepositWatcher::from_state` checked height, containing block hash and duplicate
map keys, but trusted the persisted `requirement`, `phase`, map key, chain,
amount, recipient and relationship to `credited`.

Discriminating examples against the baseline:

* A 1001-BLCH deposit at depth one with its requirement changed to
  `Automatic { depth: 1 }` restored successfully, bypassing the review tier.
* A map key differing from `event.deposit_id()` restored successfully; the
  watcher's dedup identity and the downstream mint identity could diverge.
* A deposit marked `Creditable` at depth one, or a mature credit with an empty
  durable credit set, restored successfully.
* Wrong-chain, zero-amount and zero-recipient events could enter through restore
  even though the transaction scanner refused them.

The restore now recomputes the requirement from the amount, derives the expected
phase from the journal depth and tier, binds the key to the event, validates
deposit facts, and requires the durable log for an automatic credit. Height
conversion is checked before indexing, including on narrower targets.
`from_state_for` additionally compares the snapshot's vault set and chain ID
with independently trusted configuration supplied by the host.

This is consistency validation, not authentication. Someone able to replace the
entire snapshot with a coherent forgery or roll back all protected history is
outside the guarantee. Persist and authenticate the credit log independently
enough that restoring an older snapshot cannot reopen past mints.

### BRG-02 — Credit eligibility was sticky across depth loss

The baseline aged only `Pending` deposits. After a deposit reached K=24,
truncating descendants while retaining its containing block left the phase
`Creditable`, even at depth one. The documented restart mint worklist returned
that deposit, allowing a not-yet-performed mint to be retried below its gate.

The watcher now recalculates eligibility on each accepted view. Falling below K
demotes the phase and emits `ConfirmationsLost`; the host must cancel pending
mint/review work. The durable automatic credit set survives. Returning to K does
not emit a second `Creditable`, but the idempotent restart worklist can expose the
deposit again. Removing a previously credited deposit still raises the permanent
reorg alarm even while its current phase is `Pending`.

The worklist is also disabled immediately after restore or a refused sync. A
successful sync is required before retrying a mint. A restored journal is not
treated as evidence of a current source view.

### BRG-03 — Missing data was interpreted as a reorg

The original rewind loop treated `block_at(h) == None` as proof that block h had
disappeared. A source advertising the same tip but temporarily returning no
blocks could erase the journal, drop deposits and generate permanent credit-reorg
alarms. Earlier protection against a parent mismatch did not protect this path.

`try_sync` now returns a typed `WatcherSyncError`. Missing data at or below a
reported tip, wrong heights, inconsistent linkage, changed sampled endpoints,
and an unavailable/empty source cause a refusal. The candidate common prefix and
new blocks are discovered before any durable state changes. Only after validation
does the watcher rewind, scan and age deposits. An error leaves the serialized
`WatcherState` unchanged and disables the ephemeral mint worklist.

The existing `sync` signature remains as a compatibility wrapper: it emits an
empty update list on error. Hosts should migrate to `try_sync` to distinguish
"nothing changed" from "source refused". A coherent shorter chain remains a
valid reorg observation. An empty source is unavailable, not permission to delete
all history. A mid-call reorg is retried using the next settled view.

These checks do not implement a Byzantine snapshot protocol or prove L1
canonicality. A dishonest source can fabricate a consistently linked chain;
block validity and a trusted L1 domain must be established by the host.

### BRG-04 — Mathematically finite work was operationally unbounded

Bounding the former roll-forward loop by a caller-reported `u64` tip did not give
an operational limit. A synthetic provider could return endless linked blocks
under a huge reported tip, consuming memory and CPU before returning updates.

`DEFAULT_SYNC_LIMIT` is 1024. `try_sync_with_limit` appends at most the selected
number of blocks and refuses a rewind exceeding that number of journal entries.
Catch-up resumes in subsequent calls; deposits age using the verified local
journal depth, never the unprocessed reported tip. There are at most
`2 * limit + 4` `block_at` requests per call. A regression advertises `u64::MAX`
and enforces a small request budget without actually performing unbounded work.

The staging allocation contains the new suffix only. It does not clone the
entire journal or durable credit set for each call. This is a block-work bound,
not a total memory/time bound: individual blocks, RPC calls, the number of
tracked deposits, and retained history still require host resource limits.

### BRG-05 — The deployment validator did not enforce the withdrawal predeploy

The typed validator pinned WBLCH but accepted a configuration with no
`L2BlochBridge`, a moved bridge, or duplicate names/addresses. A genesis consumer
could consequently omit the withdrawal entry point or resolve address collisions
according to insertion order.

Both required predeploys are now checked. `L2BlochBridge` must be at
`0x4200000000000000000000000000000000000010`; WBLCH retains its existing fixed
address. Zero addresses, empty names, duplicate names and duplicate parsed
addresses are refused. This validates configuration; the repository still has
no actual genesis deployment implementation.

### BRG-06 — Symlink traversal bypassed lexical confinement

Rejecting absolute paths and `..` components did not prevent a relative source
path from following a symlink outside the crate. Existing source paths now
resolve to their canonical target, which must remain under the canonical base
directory. The regression creates an isolated temporary outside source and an
in-crate symlink, then verifies refusal and cleans up the fixture.

This does not defend against a concurrent filesystem attacker replacing paths
between validation and reading/compilation. Hosts must validate an immutable or
read-only source checkout. Missing files remain typed missing-source failures.

## Invariants checked

1. **Credit gate:** an exposed automatic credit belongs to the configured chain,
   has a nonzero recipient/amount, and has current local depth at least K(amount).
   The review tier never automatically enters the credit log.
2. **Durable dedup:** accepted syncing only adds IDs to `credited`. Rewinds,
   demotion and re-mining do not delete them or emit a second credit for an ID.
3. **Failure isolation:** an explicit sync error cannot alter the serialized
   journal, tracked deposits, credit set or permanent alarm log.
4. **Withdrawal arithmetic:** multiplying any `u64` atom amount by 10^10 fits
   `u128`; withdrawal conversion refuses remainders and overflow. Solidity
   rejects zero amount, zero recipient and unrepresentable atom amounts.
5. **Proof identity:** the leaf is Keccak of the five canonical ABI words,
   including the distinct padding rules for `address` and `bytes20`. Rust,
   Python and executed Solidity agree on a leaf and 7/17-leaf multi-epoch roots.
6. **Contract atomicity/access:** failed withdrawals roll back token balances,
   allowance consumption, native balance, nonce and tree count; both withdrawal
   functions share a reentrancy guard. Only the system alias advances epochs;
   only the operator posts roots and marks releases.
7. **Release refusal:** the real checklist evaluator retains `Scaffold` outcomes
   for missing proof verification and rate limiting. The best evaluated verdict
   remains `ScaffoldBlocked`; EVM bookkeeping/inclusion alone cannot authorize a
   custodial L1 payout.

These are code-level arguments and executable finite tests. No exhaustive proof
over every state, consensus history, compiler or integration is claimed.

## Optimization and contract review

`WithdrawalQueue::prove_at` previously folded the same historical tree prefix
once for its root and again for its proof. `ReferenceTree::root_and_proof_at`
returns both from one fold. This removes one complete redundant hashing pass;
asymptotic O(n) proof generation and leaf retention remain. No measured
end-to-end throughput or Solidity gas improvement is claimed.

The three existing contract sources and their deployed-bytecode pins remain
byte-identical to the baseline. Execution tests add evidence for their existing
guards without changing the normative leaf/root format. WBLCH updates the
withdrawer's balance before the native transfer; the bridge additionally guards
both entry points. Tests replace the trusted wrapper with deliberately malicious
test implementations to exercise cross-function reentry and an underpaying
unwrap. The relevant general principles are documented in the pinned
[Solidity 0.8.24 security guidance](https://docs.soliditylang.org/en/v0.8.24/security-considerations.html#reentrancy).

## Integration changes and residual blockers

* Restore with `from_state_for` using trusted config, handle `try_sync` errors,
  and successfully resync before using `creditable()` for pending mints.
  Catch up in bounded calls; explicitly select a larger bound for a verified
  deep rewind. Hosts with exhaustive `WatcherUpdate` matching must handle
  `ConfirmationsLost`. It cancels pending mint/review work; it cannot undo a
  mint already executed by another component.
* Old snapshots that contain inconsistent derived fields are intentionally
  rejected. Rebuild/reconcile from authenticated history while preserving the
  durable credit and alarm records. Never treat restore failure as permission
  to clear dedup history or silently start an empty watcher.
* Custodians can still steal reserves; the public reserve inequality detects
  an accounting deficit and does not constrain vault keys. The caller supplies
  reserve observations, including the proposed post-payout statement. A real
  signer must bind the exact payout, pending liability, supply and named chain
  view, and recover broadcasts through an idempotent durable payout outbox.
* No finite confirmation depth proves canonicality on a majority-attackable
  PoW chain. This review did not measure current Bloch hashrate, node security
  or deployment status. Reorgs can invalidate previously credited backing.
* The withdrawal leaf still lacks explicit chain/bridge/genesis domain
  separation, and the root does not commit to leaf count. Sharing roots or
  payout domains between deployments must remain disabled until a versioned
  protocol migration binds these values consistently across every component.
  The low-level zero-leaf proof behavior remains documented; message-level
  verification recomputes the leaf and does not accept a supplied leaf hash.
* The real FRI verifier, rate limiter, RPC validation, native-supply derivation,
  signing and payout service remain unimplemented here. Public lifecycle and
  checklist structs represent observed/operator-asserted facts, not capability
  tokens or authenticated authorizations; do not deserialize attacker-provided
  `ReleaseEligible`/`AllPass` data into a signing decision.
* The journal, tracked deposits, credit history, alarm history and reference
  Merkle leaves still grow with history. Production storage needs retention
  and authenticated checkpoint design that preserves rollback/dedup semantics.
  Source containment assumes no concurrent filesystem mutation.
* WBLCH retains WETH-style behavior: forced native transfers can make
  `totalSupply()` exceed the sum of holder balances, approvals have standard
  allowance replacement semantics, and transfers to the zero address are not
  prohibited. Integrations must use the actual accounting model. Posted verifier
  roots remain operator claims and append-only per epoch; a wrong root has no
  correction mechanism in this design stub.

The changes strengthen this repository's implemented boundaries. Production
activation still requires the missing components, coherent protocol/domain
specification, deployment-specific review, and an independent external audit.
