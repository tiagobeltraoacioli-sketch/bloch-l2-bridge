# All bridge routes in one tree: index (integration line `codex/bridge-allnets-r17-20261117`)

Status: UNAUDITED integration of the route lines; nothing is deployed; every address is `TBD-deploy`. The Ethereum
bUSDC bridge is the audit candidate (freeze `cc2511a`); every other route needs its own external audit and the owner's
ceremony before any real funds. Integrator: agent 355 (round 17), agent 375 (round 18).

## 1. What is in this tree and how it got here

Each route is developed on its own line and merged here by `tools/allnets/remerge.py` from the line's PUBLISHED tip
(`origin/<branch>`), in the order of `tools/allnets/lines.json`. Before every merge commit, `tools/allnets/mergecheck.py`
proves that no line (and, for JSON, no constraint) that either side added is missing from the result; a resolution
that would drop one is refused unless justified in writing (`tools/allnets/merge-justifications.json`). The commit taken
from each line is in `deployments/allnets/merge-lock.json`. Never merged: the branches listed under `never` in
`lines.json` (a parked contract in their history; the Base signer prototype); the parked contract's path may never
occur in this history (checked by the test entry point).

true only when the route's own source says launchable AND no finding of severity Medium or above is open in

## 3. One deploy tool

`python3 tools/deploy-pontes/deploy_pontes.py routes` lists every route, its launch status and how its L2 token is
deployed; `deploy_pontes.py route NETWORK COMMAND ...` runs that route's path with its committed config. The L2 token
is always the frozen `BridgedStablecoinV3` (creation keccak `0xe560441f…1de7`). A source chain id other than 1 and the
EVM launch registry's networks is accepted only by the data rule of `tools/deploy-pontes/routes.py`
(`source_refusal`); chain id 1 accepts only the Ethereum bridge's token (`Bloch Bridged USDC`, `bUSDC`). Base and BNB
Smart Chain are refused by every tool, with no override. Known gap: the Bitcoin path (`btc_deploy.py token`) prints
the creation data and verifies; it has no plan / run / record of its own.

## 4. Cross-route isolation (what is checked, and by what)

| Property | Check |
|---|---|
| network ids, L2 symbols, L2 names, source chain ids (256-bit), source-domain labels: unique | `registry.py` C1-C4 (write refuses, check fails), tests in `tools/allnets/test_registry.py` |
| every L2 token the frozen BridgedStablecoinV3 on 700770 | C5 |
| fee recipient of every route = the owner's address on that network kind | C6 |
| one committee shape (scheme, threshold 5, switch 6, pause-only guardians, pause seconds) | C7 |
| a release certificate of one route is refused by every other route (81 cells), a mint certificate likewise (100 cells), even with one vault address and one token address for all | `tools/allnets/test_cross_route.py` (each route's own digest code; throwaway 5-of-7) |
| a token config of one route cannot be deployed under another route's source chain id | `tools/deploy-pontes/test_routes.py` |
| every path a route line owns is byte-identical to its merged tip | `test_all.py` integration stage |

What separates two routes' certificates is the source chain id word in the signed digest (the EVM-shaped vaults,
TRON and Solana share one digest layout) or Stellar's own tags; the matrix's control test shows that two routes with
one chain id would accept each other's certificates, so check C3 is load-bearing. Bitcoin releases are Bitcoin
transactions signed over BIP-143 data of the route's own thread: not comparable certificates (stated as an argument
in the test file).

## 5. One test entry point

`python3 tools/allnets/test_all.py OUTDIR [STAGE...] --tools TOOLS.json --port-base N`: stages integration, forge,
offline, ethereum, evmnets, forks, bitcoin, solana, tron, stellar, scripts. A stage whose toolchain is not named in
`TOOLS.json` is recorded NOT RUN with the reason; it never counts as a pass. The table of each run is
`OUTDIR/table.json`; the integrator's report lists each run with its tip.

Two conditions of the environment are part of the entry point since round 19, so that a run on another host means
the same thing:

- **File-mode mask.** `--umask OCTAL` runs every suite under that umask and writes it into the first line of
  `summary.txt`. No suite may depend on the caller's umask: the product rules refuse a credentials directory, a key
  file or a verifier binary that group or others can write, and a fixture that leaves the mode to the umask passes on
  one host and fails on another (it did: `test_relayer_key` and the four `scripts/tests/test_custody_deployment_*`
  classes under umask 002). The fixtures set explicit modes; the rules are pinned by
  `test_a_credentials_directory_made_under_umask_002_is_refused` and
  `test_a_group_or_other_writable_verifier_is_refused`.
- **Crates of the custody verifiers.** `scripts/tests` builds the Rust verifiers with `cargo build --offline`
  (`--locked`, toolchain 1.94.1). On a host whose cargo registry does not hold every crate of `Cargo.lock`, three
  test classes stop in `setUpClass` ("failed to download"). Nothing is vendored. On an online host, once:
  `CARGO_HOME=<dir> ~/.cargo/bin/cargo +1.94.1 fetch --locked` at the repository root, then name `<dir>` as
  `cargoHome` in `TOOLS.json` (or leave both out to use the default `~/.cargo`).
